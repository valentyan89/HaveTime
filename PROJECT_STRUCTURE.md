# Структура проекта HaveTime

Этот проект построен по принципам **Clean Architecture** и разделен на слои: **Data**, **Domain** и **Presentation**. Это позволяет отделить логику хранения данных от логики отображения.

## 📂 Основные слои и их назначение

### 1. 🟢 Слой Domain (Бизнес-логика)
Находится в `com.example.havetime.domain`. Это "сердце" приложения.
- **`model/`**: Описания объектов, с которыми работает приложение (`Activity`, `TodoItem`, `TimeInterval`).
- **`repository/`**: Интерфейсы (контракты), которые описывают, *что* должен уметь делать репозиторий (например, `ActivityRepository`).
- **`usecase/`**: Одиночные действия пользователя (например, `AddTodoUseCase`). Каждый UseCase берет репозиторий и вызывает нужный метод.

### 2. 🟡 Слой Data (Данные)
Находится в `com.example.havetime.data`. Отвечает за сохранение и получение данных.
- **`local/`**: Локальная база данных SQLite через библиотеку **Room**.
    - `entity/`: Как данные хранятся в БД (`ActivityEntity`).
    - `dao/`: SQL-запросы к базе.
    - `ActivityDataBase.kt`: Главный класс базы данных.
- **`remote/`**: Работа с сервером через **Ktor**.
    - `api/`: Описание сетевых запросов.
    - `client/`: Настройка сетевого клиента.
- **`repository/`**: Реализация интерфейсов из Domain. Решает, брать данные из БД или с сервера.
- **`mapper/`**: Преобразует объекты данных (`Entity` или `Dto`) в объекты бизнеса (`Domain model`) и наоборот.

### 3. 🔵 Слой Presentation (Интерфейс)
Находится в `com.example.havetime.presentation`.
- **`screens/`**: UI-экраны на Jetpack Compose.
- **`CalendarViewModel.kt`**: Хранит состояние экрана и обрабатывает действия пользователя, вызывая UseCases.

---

## 🔄 Как данные сохраняются и передаются (Data Flow)

1. **Пользователь** нажимает "Сохранить" на экране.
2. **ViewModel** вызывает `AddTodoUseCase`.
3. **UseCase** вызывает метод `addTodo()` в `ActivityRepository`.
4. **ActivityRepositoryImpl** (в слое Data):
    - Сначала сохраняет активность в локальную базу данных (**Room**) через `ActivityDao`.
    - (В будущем) Вызывает сетевой запрос через `AuthApi` или `ActivityApi`, чтобы отправить данные на **Сервер**.
5. База данных Room обновляет поток (`Flow`), и **ViewModel** автоматически получает обновленный список, который отображается на экране.

## 🗺 Карта файлов для работы

### Где создавать новые экраны?
Работай в папке `presentation/screens/`:
- `day/`: Экран дня и диалог добавления.
- `week/`, `month/`, `year/`: Новые папки для соответствующих представлений.
- `test/TestMapScreen.kt`: Пример работы с картой (Osmdroid).

### Как добавить новое поле (например, описание)?
1. Добавь поле в `domain/model/Activity.kt`.
2. Добавь колонку в `data/local/entity/ActivityEntity.kt`.
3. Обнови `data/mapper/ActivityMapper.kt`, чтобы поле переносилось между слоями.
4. Обнови UI, чтобы пользователь мог вводить это поле.

### Куда отправляются данные на сервер?
Сейчас сетевой слой настроен в `data/remote/client/KtorClient.kt`. 
Чтобы данные реально уходили на сервер:
1. Опиши метод в интерфейсе репозитория (`ActivityRepository`).
2. Реализуй его в `ActivityRepositoryImpl`, используя `HttpClient` для выполнения POST/PUT запросов.

## 🚀 Твой план разработки
1.  **Диалог добавления**: Создай красивый диалог в `presentation/screens/day/AddActivityDialog.kt`, который принимает `TimeInterval` и `Location`.
2.  **Экран Дня**: Выведи список из `viewModel.activities` в виде таймлайна.
3.  **Синхронизация**: В `ActivityRepositoryImpl` добавь вызов сервера после успешного сохранения в БД.
4.  **Навигация**: Настрой переключение между День/Неделя/Месяц в `MainActivity.kt`.
